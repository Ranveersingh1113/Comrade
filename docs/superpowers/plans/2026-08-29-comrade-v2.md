The findings doc remains authoritative for *reasoning*; this file is authoritative for *order*.

## Global Constraints

Copied verbatim from the findings doc. Every task's requirements implicitly include this section.

1. **Migration policy (§8, §16.5):** any index on an *existing* table uses `CREATE INDEX CONCURRENTLY` (outside a transaction); any check constraint on an existing table is added `NOT VALID` then `VALIDATE CONSTRAINT`.
2. **Reads borrow the requester; writes act as the app** (§4.1, §16.3). The agent is a lens, not an actor.
3. **The agent never initiates a group post** (§13.1). Two kept cases are not exceptions: a direct reply to an `@comrade` invocation, and the compiler's memory diff card (a system notice). Repo events, tool status and scheduled summaries reach the group room **never**.
4. **Unknown tool → `outbound`, `writes=true`, `needs_human=true`** (§15.4). Fails closed.
5. **The chokepoint governs tools that leave the sandbox; it does not govern the shell inside it** (§15.5). Gate `surface=outbound` and `surface=db`; let `surface=sandbox` run free.
6. **Only team-scoped content enters the shared sandbox** (§17.4). No private-thread context, no per-member credentials, no personal tokens.
7. **The sandbox holds no credentials, ever** (§17.3). Egress passes through a proxy that injects the real token at the network layer.
8. **GitHub writes use the installation token, never user-to-server** (§16.3). Writes appear as `comrade[bot]`.
9. **Merge, protected-branch write, force-push, secrets and Actions config are capabilities never held** (§16.2, §16.4). Don't ask, don't hold.
10. **Compiled facts cite human-verified artifacts** (merged PR, review, human comment) — never the agent's own claims about its own work (§22.3).
11. **`spotlight()` before every LLM call** on any attacker-controlled text. Extending to the repo path is a prerequisite for any repo-reading tool (§16.6).
12. **Paying buys continued service and nothing else** (§23.1) — no visibility, no vote, no member removal, no consent override, no private-thread access. `comrade_agent` gets no grants on `subscriptions`, not even `select` (§23.4-1).
13. **Memory-as-hint:** the wiki is a record, not an authority. Action-bearing facts are verified against live state.
14. **No LLM call inside a transaction.** Verified-correct today on both compile paths; keep it.

### The five things that make it feel crude

These are my read, not the doc's. They are what "not usable by anyone" actually means:

1. **🔴 The agent has no conversation memory whatsoever.** `agent/runtime.py:72` creates a *brand-new* `InMemoryRunner` session per turn and sends only `user_text`. It cannot remember your previous message. The doc files this at §19-12 as an architecture item; it is in fact the single loudest usability defect in the product.
2. **🔴 The agent cannot read the room.** Five tools, none of which reads `messages`. It answers questions about a conversation it cannot see (§5).
3. **🔴 Every wiki fact reaches the model as an undated bullet.** `pipeline/wiki.py:76`. Measured 39-point temporal-reasoning cost (§20.3.1), and page descriptions are never written (§2.3) so the recall index is titles-only.
4. **🟡 Turns are synchronous and unbounded.** `/agent/turn` blocks a threadpool worker; no `max_llm_calls`; a loop runs to the model's own limit.
5. **🟡 Nothing the agent proposes ever teaches it anything.** Rejections are terminal and silent (G3).

### Confirmed-latent, not exploitable today

- §2.1 `ag_messages` is team-scoped, not thread-scoped — the agent role can `select` every member's private thread. **Verified still present** at `20260612095500_rls.sql:248` and `20260612120000_action_consent.sql:31`. ## Part III — Sequencing logic

Where this differs from §19 + §21, and why.

### The four rules I sequenced on

1. **Deletions before additions.** Every removal shrinks the surface the next feature is written against. F1/F2/F3 delete code across four layers and change the shape of the consent record; writing the chokepoint against the pre-deletion shape means writing it twice. §13.7 already establishes F2-before-F3; I extend the same logic to the whole phase.
2. **Infrastructure before semantics.** The connection pool changes no behaviour and touches one file. Do the risky semantic work on a fixed foundation, not the reverse.
3. **The gate before the tools it gates.** Phase 2 adds eight tools. If the registry lands first, each is classified at birth and an unclassified one fails closed. If it lands after, it is a retrofit across eight call sites plus a migration of `_TOOL_TIER_FLOORS`.
4. **User-visible defect beats architectural tidiness at equal cost.** This is where I diverge most.

### Three deliberate departures from §19

**A. ADK session storage moves from position 12 to Phase 1.**
§19 files it as an architecture item. It is not. `agent/runtime.py:72` builds a fresh session per turn, so *the agent cannot remember your previous message*. For a product described as "a silent teammate," that is the defect a first-time user hits in under sixty seconds. Same slice carries `RunConfig.max_llm_calls` — today there is no turn cap at all, so a loop runs to the model's own ceiling on the team's budget. Cost of the slice is one migration plus ~30 lines; value is the difference between a demo and a teammate.

**B. The cheap-columns migration moves from position 13 to *before* rejection feedback.**
§19 puts rejections-reach-the-model at 8 and the columns at 13, but G3 needs a rejection-reason column on `consent_queue` to carry the *why*. Inverted as written. One migration, done once, unblocks G3, `propose_batch` (`batch_id`), proposal→turn tracing (`agent_run_id`), cancellation (`cancelled`), subagent runs (`agent` trigger type) and the billing input (§23.4-3). It is the highest unblock-per-line item in the document and it is currently ranked 13th.

**C. `agent_steps` moves ahead of job-backed turns.**
§19 has job-backed turns at 9 and `agent_steps` at 10. Job-backed turns rewrite how a run is recorded; fixing the recording table *after* rewriting the recorder means touching it twice. `append_step` is also the single worst function in the codebase — 20 connections and an O(N²) jsonb rewrite per 20-step turn (§3.2) — and long turns make both worse, so it must be fixed before turns get longer, not after.

### What I kept from §19 unchanged

- **F1 first, before any message-reading tool.** Non-negotiable; §2.1 goes live the moment `messages_search` exists.
- **The registry at position 3**, scoped to `outbound`/`db` (§15.5), unknown fails closed.
- **GitHub as an independent track.** §19-7's note is the most commercially important sentence in the document: the repo→wiki path needs no sandbox, *is* the free tier, and if the harness slips Comrade is still a working product. Phase 3 has exactly one dependency on Phase 0 (the pool) and none on Phases 1–2. **Give it to a second person on day one.**
- **The sandbox last, behind its three prerequisites** (pool, job-backed turns, `agent_steps`), with the free/paid line falling where §23.4-4 says it does — while honouring §24.4's warning to re-check that alignment rather than inherit it.
- **The trust ratchet (G4/G5) genuinely last.** §12 proves the agent has no autonomous trigger and §13 removes the one tool that could have produced unsolicited output. A brake on a vehicle with no engine is not a feature.

### Critical path

F1 ─┬─ F2 ─ F3 ─┬─ F8 (registry) ─┬─ F16/F17/F33-F36 (tools)
    │           │                 └─ F45 (ratchet, Phase 6)

                ├─ F11 (sessions) ─ F12 (room lock)

## Part V — Track D: the product layer the doc does not cover

The findings doc contains zero items in these categories because it is an agent-architecture audit, not a product audit — which is exactly why they went unrecorded, and why "the previous version was not usable by anyone" is not fully answered by Phases 0–4.

## Part VI — Execution protocol

- **One phase = one branch.** Merge to `master` at each phase boundary; the current `feat/frontend` branch merges first.
- **Every task ends green.** `uv run pytest` + `npm test` + `npm run test:integration`. Live tests (`-m live`) run at phase boundaries only.
- **Every migration is reversible or explicitly one-way**, and states which. Per Global Constraint 1.
- **Deletion tasks must produce a red suite first.** §13.5 is the warning: eight of ten references to `post_group_message` keep passing after the tool is deleted, because `propose_action` performs no `tool_name` validation. Add that validation (F8) so removals fail loudly — but until F8 lands, *manually verify* each deletion instead of trusting a green suite.
- **Append to the findings doc, don't rewrite it.** Per §24.5-2: `grep -n '^## '` immediately before appending, and put the section number in the commit message.

Detailed bite-sized task breakdowns (failing test → run → implement → run → commit) are written **one phase at a time**, immediately before that phase is executed, so they reflect the tree as it actually is rather than as it was predicted to be.
