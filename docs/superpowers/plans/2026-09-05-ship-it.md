# Ship it — the cut from 25 tasks to a deployable system

Written 2026-09-05, under a time limit. Supersedes the sequencing of
`2026-09-04-production-multiplayer-harness.md` (that plan stays the spec for
the tasks named below; only the ORDER and the SCOPE change here).

**Goal:** a stranger opens a URL, signs up, connects a repository, and gets
value — with their code and their bill safe from other tenants.

**Decisions taken 2026-09-05:** cloud host (Fly/Render/Railway class), and
strangers may connect repositories. Both answers make security work
mandatory rather than deferrable.

## Cut

| plan task | verdict | why |
|---|---|---|
| 15 isolated thread workspaces | **ship** | `workspace_for(team_id)` is one checkout per TEAM. Two members at once collide. The product's headline claim is false without this. Carries the `capture_patch` wrong-repository corruption bug. |
| 16 sandbox hardening | **ship (slice)** | Strangers run code. Non-root UID, CPU/memory/PID/time limits, no host secrets reachable. Full egress-proxy work deferred. |
| 23 atomic quotas + control-plane role | **ship** | Non-atomic token caps on a shared API key is an unbounded bill. Production must not run as the table owner. |
| 25 readiness + operations | **ship** | `/ready`, structured logs, graceful drain, ops doc. Cannot run in a cloud without it. |
| — packaging + deploy | **ship** | Not a plan task and the actual blocker: no app Dockerfile, no compose, no runbook exists. |
| 14 work board | defer | The Tasks screen already works. Duplication is a wart, not a blocker. |
| 17 previews, 18 CI feedback, 19 attachments, 20 memory scopes, 21 skills, 22 MCP | defer | All additive. None gate a first real user. |
| 24 eval release gate | defer | Needs repeated live runs; the scenario baseline is red against the live model by design (handoff finding 5). |

## Order

Each step ships on its own. Focused tests during each; the full
`scripts/gates.sh --with-reset` only where marked — it costs ~20 minutes.

- **A. Task 15** — per-thread Git workspaces, `capture_patch` ceiling fix.
- **B. Task 16 slice** — non-root sandbox UID, resource limits, secret reachability.
- **C. Task 23** — atomic reservation, `Role.CONTROL`, ADMIN out of production. **GATE.**
- **D. Task 25** — `/ready`, correlation logs, graceful shutdown, `docs/operations.md`.
- **E. Packaging** — Dockerfiles (api, worker, frontend), compose, `.env.production.example`,
  release migration step, deploy runbook. **GATE**, then deploy.

## The deployment constraint, named up front

`repo_run` needs a Docker daemon. A normal app container on Fly/Render/Railway
does not have one. So the worker lands on a host with a Docker socket (a Fly
machine running Docker-in-Docker, or a plain VM); API and frontend go anywhere.
Packaging assumes that split rather than pretending one image fits.

## What a human must do, not Claude

Creating accounts, entering credentials, and authorising OAuth are the
operator's, by policy. Everything is built deploy-ready and the runbook gives
the exact commands: Supabase project, Gemini key, GitHub App, host secrets.
